A running reader doesn’t mean your data arrived.

Open-source change data capture from IBM i (AS/400) to Snowflake, in your own AWS or GCP account, with no Kafka and no license key. We report journal reading, Snowflake delivery and event-count reconciliation separately for each table.

Preview, DEV/INT only. No production qualification, no SLA. Source 0.4.3 candidate, latest published prerelease 0.4.2, last observed release 0.3.5 (2026-10-12). In the 0.3.4 cold-warehouse trial, 3 of 4 targets missed our 10 s bar; a later 0.3.4 run passed on all four. Evidence

From journal receiver to Snowflake

We apply change data capture to Db2 for i journals on IBM i (formerly AS/400 and iSeries): a Java/JTOpen reader reads entries over TLS from the last acquired position.

Each table shows its state (Capture enabled, Copying, Paused, Attention or Stopped), lag, throughput and row counts. A missing value shows “—”, never a zero or a silent estimate. “Not measured” means no evidence; Measured means recorded and timestamped. Capture enabled does not prove delivery. The operator guide lists the tabs.

Pause and resume are in the cockpit. Removing a table, restarting an initial copy, replaying a journal range or suspending the organization needs human approval; an agent connected through MCP cannot approve its own action without administrator preauthorization, and every call is audited. Retention of RAW data and checkpoints after complete site loss was verified on historical versions only (Evidence).

Try it

Start with compatibility and prerequisites; the cockpit is unauthenticated on loopback by default, so read the security policy before exposing it.

The cockpit with generated data

git clone https://github.com/quadringent/quadringent-ce.git
cd quadringent-ce
npm ci --prefix ui
node ui/scripts/build-demo.mjs --serve

Needs Node 24 or 26; open http://127.0.0.1:8870/#/cockpit. A Synthetic demo: no IBM i, Snowflake or cloud connection, network requests blocked. Not a release qualification.

What we have measured, and what we have not

  • Measured

    0.3.5, 2026-10-12. A fresh initial copy on four targets (AWS VM, EKS, GCP VM, GKE), 110 mirror rows and 110 history C images each, and an EKS rollback and re-upgrade on the same PostgreSQL PVC. Receipt: runtime-0.3.5.json.

  • Measured

    0.3.4, 2026-10-12, 18:13 UTC. Reconstruction on new PostgreSQL PVCs, 4 reader SIGKILL recoveries and 8 cold/warm observations within 10 s, from 3.763 s to 8.876 s between the SQL statement and the mirror row. Upper bounds, not a P95 and not an SLA. Receipt: recovery-0.3.4.json.

  • Measured

    The earlier 0.3.4 trial passed our 10 s bar on 1 of 4 targets; the worst took 13.641 s from SQL start to mirror. Neither trial is a P95 or an SLA. Summary: qualification-0.3.4.json.

  • Not tested

    On the 0.4.3 candidate source and the published 0.4.2 prerelease: native CDC, reader outage, latency and complete cloud-loss recovery need fresh qualification; history does not stand in for them.

  • Not measured

    Snowflake cost per 24 h, and the CPU and I/O cost of the reads on your IBM i.

Working with us

Community is free: engine, API, cockpit and chart under Apache-2.0, with no activation key or commercial table limit. IBM i, cloud and Snowflake costs stay yours. No paid offer is launched or priced.

If there is demand, we would offer installation and a pilot first, with scope and acceptance criteria agreed beforehand. Support would be a separate agreement after the pilot, managed hosting only once a real need is confirmed.

Email quadringent@proton.me to discuss a pilot privately, without a GitHub account, or file a public pilot interest request (the issue and your account name are publicly visible). Send no credentials, access, private hostnames, customer data or attachments.

Next: technical discovery, written scope, separate pilot decision. We never accept a request automatically and make no response-time commitment.
